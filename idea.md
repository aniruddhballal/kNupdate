## Section 2 — Technical build specification

## 1. Product definition

**App name:** kNupdate  
**Pronunciation:** “nupdate” (the K is silent)  
**Suggested Android application ID:** `com.knupdate.app`  
**Suggested APK filename:** `knupdate-vX.Y.Z.apk`

Build kNupdate as a deliberately small Android-only application: a **private mutual activity ledger** for close friends and family.

It is not a social network, a fitness tracker, a journal, a messaging app, an archive, a creator platform, or a productivity tool. It is a short-lived, structured way for people who already have a close relationship to quietly state that an activity happened.

The core output is plain text such as:

> Aniruddh completed an activity — Run · 5 km · 9:30 AM–10:00 AM

The update is visible only to accepted mutual connections, does not accept engagement, cannot be shared outside the app, and is hard-deleted for every recipient after a fixed expiry duration.

### Product success condition

The app succeeds if it works reliably for one person and a small close circle. It must not be designed around growth, retention, virality, creator behaviour, advertising, analytics, or feature requests.

## 2. Immutable product principles

These are requirements, not future feature opportunities.

1. **Private by construction.** There is no public profile state, public URL, discovery feed, explore page, public activity page, or follower count.
2. **Mutual connection only.** A relationship exists only after both people explicitly accept it. There are no one-way follows.
3. **No stranger discovery.** No username, name, contact, location, or global search for people. No suggested people, “people you may know,” referral programme, QR growth mechanic, or invite leaderboard.
4. **Existing relationship graph only.** A connection request is permitted only when the pair meet the mutual-connection eligibility rule defined below.
5. **Structured text only.** Activities are selected from a controlled taxonomy. Free-form titles, captions, notes, hashtags, links, images, video, audio, music embeds, location proof, attachments, and rich text are prohibited.
6. **No engagement primitives.** No likes, reactions, comments, replies, reshares, reposts, quote posts, saves, bookmarks, view counts, read receipts, streaks, badges, rankings, or leaderboards.
7. **No direct messaging.** No DMs, group chats, reply fields, inbox, typing indicators, or message notifications.
8. **No behaviour optimisation.** No recommendations, personalisation, ranking, algorithmic feed order, watch history, tracking pixels, ad SDKs, analytics SDKs, crash-reporting SaaS, A/B testing, or engagement metrics.
9. **Temporary by design.** Every activity is hard-deleted after its expiry time. No archive, restore, export, backup, deletion log, memories, highlights, “on this day,” or historical statistics.
10. **No external sharing.** Disable sharing activities through Android’s share sheet and do not expose web URLs, deep links to individual activities, copy buttons, screenshots of data, or social integrations. The app cannot prevent system screenshots, but it must not create a built-in share path.
11. **No monetisation or growth surface.** No ads, subscriptions, payments, in-app purchases, brand page, app-store listing, public website marketing funnel, or user-acquisition analytics.
12. **Finite maintenance is acceptable.** Prefer boring, stable technology and a small dependency tree. If the product ceases to work after serving its purpose, that is acceptable.

## 3. Target platform and distribution

### Platform

- Android only.
- Native Kotlin application.
- Jetpack Compose UI.
- No iOS application and no web client.
- No React Native, Flutter, or cross-platform layer.

### Distribution

- Build a signed release APK.
- Publish the APK and SHA-256 checksum on a private or unlisted GitHub Release/repository.
- Users install it manually after enabling Android’s “Install unknown apps” permission for their browser/file manager.
- Do not submit it to Google Play.
- Preserve the release signing keystore and its password securely; every later update must be signed with the same key in order to update existing installations.
- Use a clear version name and version code, but do not create in-app update nagging. At most, show a static optional “version” line in Settings.

## 4. Account and identity model

### Account creation

Use a minimal account system. Recommended initial implementation: phone-number sign-in with OTP. It gives each account a practical unique identifier without creating public discoverability.

- Ask only for: display name, phone number, and OTP verification.
- Display name: 2–40 characters, plain text, no emoji-only name, no user-selectable handle.
- Do not show a public username, profile photo, bio, pronouns, website, location, date of birth, follower count, or activity total.
- Do not import contacts automatically.
- Do not require access to contacts, location, photos, storage, microphone, camera, fitness data, SMS, or call logs.
- Phone number must never be visible to any other user.

### Profile screen

The profile contains only:

- display name;
- an “Add activity” action;
- currently unexpired activities posted by the user;
- an optional count/list of current mutual connections (names only);
- a simple Settings entry.

Once an activity expires, it disappears from the profile as well as every feed.

## 5. Connection model

### Definition

A connection is a mutual, accepted, two-way private relationship. There is no follower/following distinction.

### Eligibility rule

To avoid random connections while still allowing a trusted circle to form:

- A person may request a connection only if they share at least **two existing mutual connections** with the target.
- The app displays neither a searchable directory nor an open list of everyone’s connections.
- On the request screen, the requester may enter a private **connection code** supplied directly by the target outside the app (in person, call, or other existing channel). The app validates eligibility in the background.
- The target sees the requester’s display name and the count of shared mutual connections, not a public profile or activity history.
- The target must explicitly accept or decline.
- Acceptance creates one symmetric connection record.

### Bootstrap exception

The first small founding circle needs a way to exist before two mutuals are possible. Implement an app-owner-controlled initial allowlist:

- A configuration file on the backend contains a small list of approved phone-number hashes for seed users.
- Seed users may connect using a one-time connection code without the two-mutual rule.
- This is for initial setup only. It is not an open invite system and must not be exposed in the UI.

### Connection controls

- A user may remove a connection at any time.
- Removal immediately prevents future activity delivery in both directions.
- Removal does not expose a reason, block notice, or social signal.
- Existing activity records remain visible only until their normal expiry, unless the product owner explicitly chooses immediate removal behaviour. Recommended default: existing records are removed from the former connection’s feed immediately, then hard-deleted on schedule.
- No blocklist UI is required in v1; a removed connection cannot send a new request unless eligibility is met again and a new private code is provided.

## 6. Activity model

### Allowed activity types

Use a finite, source-controlled enum. The initial list should be deliberately small:

- Run
- Walk
- Cycle
- Swim
- Strength training
- Yoga
- Sport / game
- Study
- Read
- Work
- Cook
- Travel
- Rest
- Other structured activity

“Other structured activity” must still be chosen from a backend-configured list, not written freely by users. Examples may include meditation, volunteering, practice, or class. Do not add a free-text fallback.

### Fields

Every activity contains:

- `activity_type` — required enum;
- `started_at` — required local date/time selected by picker;
- `ended_at` — required local date/time selected by picker;
- `quantity_type` — optional controlled enum: distance, pages, minutes, sessions, none;
- `quantity_value` — optional positive decimal/whole number under a sensible maximum;
- `quantity_unit` — derived from `quantity_type`, never typed;
- `created_at` — server timestamp;
- `expires_at` — server timestamp;
- `timezone_at_creation` — IANA timezone identifier;
- `author_id` — private internal ID.

No caption, description, title, proof, link, media, location, mood, song, tagging, custom labels, or free-text field exists.

### Input constraints

- End time must be after start time.
- Do not silently correct improbable values. If a user enters 100 km, the activity can be posted; the product is not a verification system.
- Apply only basic validity limits to prevent malformed data and abuse, such as a maximum duration of 24 hours and a maximum numeric value per quantity type.
- Do not integrate Strava, Garmin, Apple Health, Google Fit, Spotify, maps, calendars, or any third-party proof source.

### Rendering rules

Use a single plain-text system template, with no user control over wording. Examples:

- `Aniruddh completed an activity — Run · 5 km · 9:30 AM–10:00 AM`
- `Maya completed an activity — Read · 45 minutes · 8:00 PM–8:45 PM`
- `Arjun completed an activity — Yoga · 6:30 AM–7:00 AM`

The display name, chosen activity, quantity, and time are the only visible data.

## 7. Feed and notification behaviour

### Feed

- The home screen is a chronological list of unexpired activities from mutual connections.
- Sort strictly by `created_at` descending. No ranking, pinning, highlights, relevance score, or recommendation.
- Every row is text only.
- Tapping a row does nothing; there is no detail screen, reaction sheet, user profile exploration, or contextual thread.
- The feed contains no infinite scroll: it ends naturally after the small current set of unexpired activity records.
- Show an empty state such as: `No current activity updates.` Do not use gamified prompts.

### Notifications

- When an activity is created, send one standard Android push notification to each current mutual connection.
- Notification content follows the same system text template.
- Tapping a notification opens the home feed only, not a dedicated activity page.
- There are no notification reactions, quick replies, grouped social summaries, read receipts, or delivery-status views.
- A user may disable notifications through Android settings. Do not repeatedly prompt them to re-enable notifications.

### Notification infrastructure

Firebase Cloud Messaging (FCM) may be used solely as delivery infrastructure. Do not enable Firebase Analytics, Remote Config experimentation, Performance Monitoring, Crashlytics, or ad products.

## 8. Expiry and hard-deletion behaviour

### Configurable expiry window

The initial deployment must define one global expiry window: **24 hours**, **72 hours**, or **7 days**. Do not allow each user to choose their own expiry, as this creates different persistence expectations.

Recommended initial value: **72 hours**. It is long enough for close connections to see an update, while keeping the product explicitly present-tense.

### Required deletion semantics

At `expires_at`:

1. Delete the activity row from the primary database.
2. Delete any activity-specific notification-delivery record.
3. Delete any cached activity payload from server cache/queue.
4. Ensure activity data does not appear in backups, logs, analytics, audit trails, exports, or soft-delete tables.
5. Clients remove the activity during the next sync; the app must also locally hide it immediately once device time passes `expires_at`.

There must be no soft deletion, trash, grace period, restore function, archive, or retained event log.

### Deletion worker

- Run a scheduled backend job at least every 15 minutes.
- The job uses `expires_at <= current server time` and permanently deletes matching activities.
- The database must automatically delete dependent rows via foreign-key cascade where appropriate.
- Do not retain deleted IDs, counts, titles, timing data, or user-level history.
- Server logs must avoid logging activity payloads.

### Local client data

- Store only currently unexpired activity data in encrypted local storage.
- On app launch, foreground resume, and periodic background sync, purge expired local records.
- Do not write activity text to a local permanent history, Android backup, clipboard, share cache, or file storage.

## 9. Screens and user flows

### 9.1 Onboarding

1. Minimal statement of purpose: `A private, temporary activity ledger for people already close to you.`
2. Enter display name.
3. Enter phone number and verify OTP.
4. Explain the non-features: no public account, no followers, no likes, no messages, no archive.
5. Land on an empty feed.

No tutorial carousel, referral prompt, permissions fishing, or contact-sync prompt.

### 9.2 Add activity

1. Tap `Add activity`.
2. Pick activity type from the controlled list.
3. Set start and end time.
4. Optionally add a permitted quantity using unit-appropriate controls.
5. See the exact plain-text sentence that will be sent.
6. Tap `Notify connections`.
7. Confirmation state: `Activity shared with your current connections. It will disappear in [expiry].`

Do not offer draft saving, post editing, caption preview customisation, hashtags, links, photos, or a “share elsewhere” option.

### 9.3 View feed

1. Open app or tap notification.
2. View chronological, text-only activity rows.
3. Do not interact with a row.
4. Open own profile only through a small navigation control; do not browse others.

### 9.4 Manage connections

1. Open `Connections`.
2. View a simple private list of current connection names.
3. To initiate a request, enter the target’s connection code supplied outside the app.
4. If the mutual rule is met, submit request.
5. Target accepts or declines.
6. Allow removal of any connection through a confirmation dialog.

No user search, suggested connections, social graph visualisation, follower list, “mutuals” browsing, or import contacts.

### 9.5 Settings

Only include:

- display-name change;
- notification preference explanation/link to Android notification settings;
- current expiry window (read-only);
- app version;
- sign out;
- delete account.

Account deletion must permanently delete the account, device tokens, connection records, pending requests, and current activity records. It must not produce an archive or recovery period.

## 10. Recommended architecture

### Android client

- Language: Kotlin.
- UI: Jetpack Compose + Material 3 only as a restrained component base.
- Architecture: single-activity app; MVVM; Repository pattern; Kotlin Coroutines and Flow.
- Networking: Retrofit/OkHttp or Ktor Client.
- Local data: Room database with SQLCipher or Android encrypted storage for tokens; retain only unexpired feed data.
- Dependency injection: Hilt, kept minimal.
- Background tasks: WorkManager only for token refresh/sync/local expiry cleanup; do not use it for engagement reactivation.
- Push: Firebase Cloud Messaging, notification-only use.
- Minimum SDK: choose an Android version that covers the intended small group; recommended minSdk 26 (Android 8.0) for simpler notification and security behaviour.
- Target SDK: current stable Android SDK at the time of build.

### Backend

Use a small, conventional backend that can be understood and maintained by one person.

Recommended stack:

- API: Kotlin + Ktor, or TypeScript + Fastify/NestJS. Prefer **Kotlin + Ktor** to keep the primary application language consistent.
- Database: PostgreSQL.
- Job runner: backend scheduler/cron process for expiry deletion.
- Authentication: OTP provider selected at build time; isolate it behind an interface so it can be changed later.
- Push provider: Firebase Cloud Messaging server API.
- Hosting: one small VPS/container or a managed platform with a single server process and PostgreSQL. Avoid complex microservices, Kubernetes, event streams, queues, data warehouses, and observability stacks.

- `phone_hash` unique, never return through API
- `display_name`
- `created_at`
- `updated_at`
- `deleted_at` must **not** be used; permanently delete on account deletion

`devices`

- `id` UUID primary key
- `user_id` foreign key
- `fcm_token` encrypted at rest where feasible
- `platform`
- `created_at`
- `updated_at`

`connections`

- `user_a_id`
- `user_b_id`

`connection_requests`

- `requester_id`
- `target_id`
- `status` enum: pending, accepted, declined
- `created_at`
- `expires_at` for automatic cleanup of unanswered requests

`connection_codes`

- `id` UUID primary key
- `owner_id`
- `code_hash`
- `expires_at`
- `used_at`

`activities`

- `id` UUID primary key
- `author_id`
- `activity_type`
- `started_at`
- `ended_at`
- `quantity_type` nullable
- `quantity_value` nullable
- `quantity_unit` nullable
- `timezone_at_creation`
- `created_at`
- `expires_at`

Do **not** create tables for likes, comments, follows, media, captions, links, reactions, views, analytics events, activity archives, search indexes, recommendation features, or user history.

### API endpoints

Authentication:

- `POST /auth/request-otp`
- `POST /auth/verify-otp`
- `POST /auth/sign-out`
- `DELETE /account`

Profile:

- `GET /me`
- `PATCH /me/display-name`

Devices:

- `POST /devices/register`
- `DELETE /devices/{id}`

Connections:

- `GET /connections`
- `POST /connection-codes` — create short-lived code for sharing outside the app
- `POST /connection-requests` — submit code, server validates eligibility
- `GET /connection-requests/incoming`
- `POST /connection-requests/{id}/accept`
- `POST /connection-requests/{id}/decline`
- `DELETE /connections/{id}`

Activities:

- `POST /activities`
- `GET /feed` — only unexpired activities authored by current connections, chronological order
- `GET /me/activities` — only the caller’s unexpired activities

There must be no endpoints for public profiles, arbitrary user lookup, search, media upload, activity update/edit, like/comment/repost, share link, history, export, recommendation, analytics dashboard, or admin moderation feed.

## 11. Security and privacy requirements

- Use TLS for all network traffic.
- Store auth tokens using Android Keystore-backed encrypted storage.
- Hash phone numbers in the database; keep any raw number only with the OTP provider if unavoidable.
- Use short-lived access tokens and refresh tokens.
- Authorise every API request server-side. A user may read only their own data and unexpired activities of current mutual connections.
- Ensure a removed connection cannot fetch new activities or an author’s profile data.
- Do not expose sequential IDs; use UUIDs.
- Rate-limit OTP requests, connection-code redemption, connection-request creation, and activity creation to prevent automated abuse.
- Avoid recording sensitive payloads in HTTP logs, server logs, analytics, exception reports, or backups.
- Provide a simple privacy notice in the repository: what is stored, who can see it, and exactly when activity data is hard-deleted.
- No third-party advertising, behavioural analytics, social-login, social graph, or data-broker integrations.

## 12. Visual and interaction direction

### Tone

- Quiet, utilitarian, restrained, and almost austere.
- It must not feel trendy, gamified, aspirational, competitive, or addictive.
- Avoid visually signalling fitness culture, influencer culture, productivity culture, or lifestyle branding.

### UI rules

- Plain background; high contrast; simple system typography.
- Use text-first rows with modest dividers.
- No profile images, cover images, gradients, animated confetti, badges, charts, progress rings, streak flames, trophies, or celebratory microcopy.
- No visible counters except a necessary, non-comparative connection list count if desired.
- No red unread badges or attention-grabbing notification dots.
- Use deliberate confirmation language instead of celebratory language.
- Keep navigation small: `Feed`, `Add`, `Profile/Settings`.

## 14. Build and test acceptance criteria

The first release is complete only when all of the following are true:

1. A user can sign in, set a display name, and see an empty feed.
2. A seed user can form an initial mutual connection through the bootstrap mechanism.
3. Non-seed users cannot request a connection without the required mutual eligibility and a target-supplied code.
4. A connection is always symmetric; there is no follow-without-follow-back state.
5. A user can create a valid structured activity with no free-text field.
6. The activity appears in the author’s and each current connection’s feed in chronological order.
7. Each current connection receives one push notification.
8. There is no control or endpoint to like, comment, reply, reshare, save, copy, edit, add media, or message.
9. An activity has no public URL and cannot be opened outside an authenticated app session.
10. No person-search, contact-import, suggested-connection, discovery, or public profile capability exists.
11. On expiry, the activity is hidden client-side and permanently deleted server-side. A database inspection after deletion finds no corresponding row, soft-deleted row, archive, or retained payload.
12. Account deletion permanently removes account and relationship data.
13. The release APK installs manually on supported Android devices and updates successfully from a later APK signed by the same release key.
14. The repository includes a concise README with build steps, APK verification checksum, environment-variable template, signing-key handling instructions, deletion semantics, and the explicit non-goals list.

## 15. Repository deliverables

Create a single repository with:

- `/android-app` — Kotlin/Jetpack Compose Android client (app display name: `kNupdate`; application ID: `com.knupdate.app`);
- `/backend` — Ktor backend;
- `/infra` — minimal deployment configuration and environment-variable examples;
- `/docs` — API contract, privacy/deletion model, and threat notes;
- `README.md` — local setup, deployment, APK release, signing, and non-goals;
- `LICENSE` — select an intentionally simple license at project creation;
- `.gitignore` — excludes keystores, secrets, `.env`, build artifacts, and database dumps.

Do not commit the Android signing key, OTP credentials, FCM credentials, raw phone data, APK user data, production environment files, or database backups.

## 16. Final implementation instruction

When building, treat every requested “social” convenience feature as out of scope unless it is already specified in this document. The app’s restraint is the product. A smaller, less convenient, deliberately non-scalable implementation is preferable to a feature-rich or growth-oriented one.
